## 1. Landscape Brief
### 1.1 Why parsing quality matters for AI systems
AI systems that answer questions from documents (for example, a chatbot over company files) never see the original file. They only see the text a parser extracts from it. If a table comes out scrambled, numbers end up in the wrong rows and the AI quotes the wrong value. If a two-column page is read line by line across both columns, sentences from unrelated topics get mixed together. If a scanned page produces no text, the AI simply says the information does not exist. These errors are silent: the AI still answers confidently, so nobody notices that the problem happened earlier, at the parsing step. Parser quality therefore sets an upper limit on the quality of the whole AI system.
### 1.2 Digital PDFs vs scanned PDFs
A digital PDF (for example, exported from Word) stores the actual text characters together with their positions on the page, so a tool can read the text directly. A scanned PDF stores only a picture of the page; it contains no text at all. To get text out of a scan, a tool needs OCR (Optical Character Recognition), which recognises letters in the image. OCR is slower and can make mistakes, such as reading "0" as "O" or dropping commas in numbers. Quick test: open the PDF and try to select text with the mouse. If nothing can be selected, it is a scan.
### 1.3 The main tools
- MarkItDown (Microsoft): converts many formats (PDF, Word, PowerPoint, Excel, HTML and more) to Markdown. Very fast and lightweight, but has no built-in OCR and uses simple text extraction for PDFs, so complex layouts and scans are weak points.
- Docling (originally IBM Research, now hosted by the LF AI & Data Foundation): uses AI models for page layout and table structure, keeps reading order, and includes OCR for scans. Handles PDF, Office files, HTML and images. Much better on complex PDFs, but slower and needs more memory, especially without a GPU.
- PyMuPDF4LLM (Artifex): converts PDFs to Markdown using the PyMuPDF library. Fast, good at headings, tables and multi-column pages, but reads PDFs only (Office formats need the paid PyMuPDF Pro).
- Unstructured: splits documents of many formats into typed elements (titles, paragraphs, tables), aimed at AI data pipelines. Not tested yet in this research.
- OCR tools for scans: Tesseract (classic open-source OCR engine), EasyOCR and RapidOCR (deep-learning OCR). Docling and PyMuPDF4LLM can call OCR engines like these; MarkItDown cannot on its own.

## 2. Method

* Test set: 13 files covering 7 document types (basic text, table with merged cells, two-column page, slides, spreadsheet, headers/footers, scanned page). All dummy content; see data/README.md.
* Tools: markitdown 0.1.8, docling 2.138.0, pymupdf4llm 1.28.2, all with default settings.
* Each document was run 3 times per tool, each run in a fresh Python process (scripts/run_benchmark.py).
* First run = first conversion in a new process, including model loading. Warm run = second conversion in the same process (models already loaded, like a running service).
* Evidence tags: **[measured]** = seen in our own test runs (source file named); **[read]** = taken from documentation or licence pages, not tested by us. Section 1 (landscape and licences) is [read] unless marked otherwise.
* Peak RAM = peak working set of the process (psutil).
* Facts found = automatic check against data/ground_truth.json (scripts/check_facts.py).
* Table intact / reading order = checked by eye; ratings and reasons in results/manual_checks.csv.
* Hardware: Intel i5-1135G7 (4 cores / 8 threads), 8 GB RAM (7.8 GB usable), no dedicated GPU; Windows 11 Home Single Language 23H2 (build 22631); see docs/setup.md.
* Coverage [measured, results/summary.csv]: data/ has 13 files, but scan.png is only the source image used to create 07_scanned.pdf, so the benchmark ran on 12 documents: 12 documents x 3 tools = 36 rows. Of these, 30 are real results. PyMuPDF4LLM opens only PDFs, so its 6 rows for .docx, .pptx and .xlsx files have status `unsupported` (0 successful runs). Docling and MarkItDown succeeded on all 12 documents.

## 3b. Day 2 findings (automatic checks, scanned page, timing)

All numbers in this section come from scripts in scripts/ and files in results/. Regenerate the tables with `python scripts/regenerate_report.py`.

### 3b.1 Table accuracy, cell by cell [measured]

Method: the correct tables were written as CSV answer keys in data/expected_tables/. Every value was checked against the generator scripts in scripts/make_test_docs/ (scripts/make_expected_tables.py), so the answer keys do not come from any tool. scripts/score_tables.py finds the best-matching Markdown table in each output and counts exactly matching cells (header cells ignore spaces, '-' and '/'). Results: results/table_scores.csv. Side-by-side views: results/table_details/.

* Sales table with merged header (02_table): every tool got all 12 body cells right; the differences are in the header. Best: Docling on the PDF, 15/16 cells. Its only error is the header "Sales (₹)" written as "Sales ( ) ₹". Worst: MarkItDown on the DOCX, 12/16. The header row is empty, the header text was moved into data rows, and "July | August" ended up under the Region and Sales columns.
* Slides table (04_slides): all tools 12/12 on both PPTX and PDF.
* Spreadsheet (05_sheet.xlsx, Invoices sheet): Docling 11/15, MarkItDown 10/15. Both drop the thousands separators that Excel displays (12400 instead of 12,400). MarkItDown also writes "NaN" for the empty cell. Staff sheet: both 8/8.
* The fact check scored all of these 100%. It cannot see cells in the wrong place or a damaged header.
* "Extra rows" in table_scores.csv counts any row that is not in the answer key, including a header split over two rows. Check with `python scripts/score_tables.py --show TOOL FILE` before calling it an error.

### 3b.2 Reading order [measured]

Method: facts in data/ground_truth.json are listed in human reading order. scripts/reading_order.py finds where each fact appears and counts the largest number of facts that appear in the correct order; the others are reported as out of order. Results: results/reading_order.csv. Details: results/order_details/.

* The only failure: MarkItDown on 03_two_column.pdf (8/9 in order). The right-column heading "Delta 9" appears inside the left-column paragraph about Orion Labs, so an AI could attach Orion Labs' facts to Delta 9. Docling and PyMuPDF4LLM pass. All tools pass on the DOCX.
* Ground-truth correction: on the first run every tool failed on 02_table and 06_header_footer. The cause was the answer key, not the tools: two facts were listed in the wrong order ("16,050" and "renegotiated vendor contracts"). The order was corrected using the line numbers in the generator script (scripts/fix_ground_truth_order.py). The facts themselves did not change, so fact scores are unchanged.

### 3b.4 Timing: model load, first run, warm run [measured]

The benchmark records three times separately (results/runs.csv): model load (load_s), first document (first_s) and later documents (warm_s). MarkItDown's first run (0.05 s) is shorter than its model load (1.34 s), which shows that first_s does not include load_s. Tables now use the median of the repeats, so one slow repeat cannot distort a result.

* Docling on PDFs: about 15 s model load + 25 s first document = about 40 s before the first result, then about 7 s per document. MarkItDown: about 1.4 s in total before the first result.
* Day 1 oddities explained: Docling's 114.8 s first run on the scan was the mean of 25.1, 292.9 and 26.4 s (one slow repeat). The 19.9 s warm run on 06_header_footer.pdf was the mean of 8.9, 9.0 and 41.7 s; that slow repeat also used much more memory (1813 MB vs about 1000 MB). It was not a model download: the OCR model files were created at 12:03 and the benchmark started at 12:23 on 12 October (file dates). The cause of the slow repeats is unknown, probably background Windows activity [not verified].
* Consequence: a parsing service must load Docling once at start-up and keep it in memory, not start a new process per request.

## 4. Observations (Day 1)

1. Fact count alone does not separate the tools on digital documents: all three found 100% of facts in every digital file they could open. [measured, results/facts.csv]
2. Structure does separate them. Only Docling (on the PDF) rebuilt the merged table header correctly ("Q3 2026 - July / Q3 2026 - August"). MarkItDown also pulled a sentence below the table into the table. On the two-column PDF, MarkItDown placed the "Delta 9" heading in the wrong position, yet still scored 100% on facts. A fact check misses structural errors. [measured, checked by eye, results/manual_checks.csv]
3. Scanned page: MarkItDown 0/6 (returned empty text with no error), PyMuPDF4LLM 5/6, Docling 6/6. [measured, results/facts.csv] MarkItDown has no built-in OCR. [read, MarkItDown docs]
4. Cost: on PDFs Docling is about 100x slower than MarkItDown (warm 4.2 s vs 0.043 s on 01_basic.pdf) and uses about 8x more memory (0.9-1.3 GB vs 115 MB). Each new process also pays about 15 s of model loading (load_s) and a slower first document. [measured, results/runs.csv; see 3b.4]
5. Docling is fast on Word, PowerPoint and Excel files (under 0.2 s), because these formats already contain structure and no AI models are needed. [time measured, results/summary.csv; reason read from Docling docs]
6. The original Office file is not always the best input: Docling handled the merged table header better from the PDF than from the DOCX, and Docling produced better slide headings from the slides PDF than from the PPTX (PyMuPDF4LLM cannot open PPTX, so for slides it was only tested on the PDF). [measured, checked by eye]
7. Spreadsheets: both tools output the formula result (36450) and dropped thousands separators. MarkItDown keeps sheet names but writes "NaN" for empty cells; Docling loses sheet names. [measured, outputs in results/markitdown and results/docling]

## 5. Preliminary recommendation (to be confirmed)

* Office files (DOCX/PPTX/XLSX) and simple digital PDFs where speed matters: MarkItDown (MIT licence, fastest, lightest), but it must never be used alone on scanned documents. [speed and scan failure measured; licence read]
* PDFs with complex tables, multi-column layouts, or scans: Docling (MIT licence), accepting higher time and memory cost. [quality, time and memory measured; licence read]
* PyMuPDF4LLM: good quality and fast on PDFs, but PDF-only and AGPL-3.0 licensed, so it needs a commercial licence or full source disclosure for business use. [quality, speed and PDF-only measured; licence read]
* Scanned documents: Docling with its default OCR (RapidOCR) found 6/6 facts in about 3 s warm. EasyOCR was as accurate but about 11x slower and needed 3 GB of memory. Treat empty output as an error. [measured, see 3b.3]
* Services: load Docling once at start-up (about 40 s before the first result on this laptop) and keep it in memory. [measured, see 3b.4]

## 6. Limitations and open questions

* Small test set (12 documents, plus scan.png as the source image; 1 page in most files); results may differ on long or real-world documents.
* PDFs were exported with LibreOffice, not Microsoft Word.
* CPU only; Docling would probably be faster with a GPU. [read, not tested]
* Resolved on Day 2: Docling's 114.8 s first run on the scan was one slow repeat (292.9 s); results now use medians. Cause of the slow repeat unknown [not verified]. See 3b.4.
* Resolved on Day 2: Docling's 19.9 s warm run on 06_header_footer.pdf was one slow repeat (41.7 s). See 3b.4.
* PyMuPDF4LLM read the scan without Tesseract installed because it used RapidOCR [measured, see 3b.3]. If no OCR engine is installed, it skips OCR silently [read: `select_ocr_function()` returns None], which gives empty output on scans. `scripts/check_text_layer.py` now flags image-only PDFs before parsing.
* OCR was tested on one clean, generated scan only; real scans (skewed, low resolution, handwriting) may give very different results.
* Table and reading-order scores use exact text matching; the rules are in scripts/score_tables.py and scripts/reading_order.py.
* Licences of EasyOCR, RapidOCR, Tesseract and Unstructured are listed as Apache-2.0 but still need to be verified.

* **[measured]** Docling does not degrade gradually: it goes from 6/6 at 8 degrees to 0/6 at 12 degrees, and from 6/6 at 50 dpi to 0/6 at 36 dpi. The failed outputs contain only `<!-- image -->` (14 characters), with no error or warning.
* **[measured]** `force_full_page_ocr=True` does not fix these cases, and costs about 2 s more per page.
* **[inferred]** Docling's layout model classifies the whole tilted or tiny page as a picture, so its text never reaches the Markdown output. Not proven.
* **[measured]** PyMuPDF4LLM uses the same OCR engine (RapidOCR) and found 5-6/6 on every page, including 20 degrees and 36 dpi. So how a tool passes the page to the OCR engine matters as much as which engine it uses.
* **[measured]** Docling + EasyOCR is the weakest and least consistent setup (2-6/6 on pages that Docling + RapidOCR read fully).
* The 5/6 results are the lost space in "Annual Summary 2026" (read as "AnnualSummary"). One fact on one page decides 5 vs 6, so differences of one fact are noise.
* Limitation: one page, one run per setup, simulated damage. A real phone photo is still to be added.

## Real public-domain documents

Five real documents, cut to 1-3 pages: IRS Form W-9 (p1), IRS Form 1040 (p1), CDC MMWR Vol. 74 No. 14 (p1-3), a CDC supplementary table (p1), and a 1958 NASA report (pages 24, 38, 259). Sources, licences and SHA-256 hashes: `data/real/SOURCES.csv`. Facts were typed by hand from the visible page, not copied from the text layer (`scripts/add_real_ground_truth.py`; 19 facts for W-9, MMWR and the CDC table). The 1040 and NASA documents have no facts yet.

* **[measured]** On the two-column MMWR, all three tools found 7/7 facts and kept the correct reading order, including the jump from the bottom of the left column to the top of the right. Real two-column text was handled better than expected.
* **[measured]** On the W-9 form, PyMuPDF4LLM found only 2/6 facts. **[read]** It turned the whole form into a table: some text is only split by `<br>` inside cells (a matching effect, the words are present), but other text is damaged: words are cut at cell borders ("Social se|curity number"), characters are lost ("rint or typ"), and "send to the IRS." is missing. Open question for the mentor: should `normalise()` treat `<br>` as a space?
* **[measured]** MarkItDown missed only the rotated margin text "Print or type" on the W-9 (5/6). Docling found 6/6 but failed reading order on the form; on a form with side-by-side boxes the correct order is debatable.
* **[measured]** `check_text_layer.py` flagged the NASA report as SCAN_WITH_TEXT_LAYER: an old scan with an invisible OCR text layer. The quality of that old text layer has not been checked yet.

## Reproducibility notes

* **[measured]** On Day 3 the full benchmark was re-run (all documents, 3 repeats) to include the new scans. Fact counts and reading-order results for all Day 1 documents were identical; timings differ slightly, as expected. Day 2 results are kept under the git tag `before-day3-benchmark`.
* **[measured]** MarkItDown's output for `02_table.pdf` differed from Day 1: the footer line "Prepared by the Zentrix finance team." moved out of the table (extra rows 2 -> 1), with the same cell score (14/16). Docling's output for the same file also changed, with the same score. The input file, the tool versions and the PDF libraries were unchanged, and MarkItDown gave identical output in 5 fresh runs (`scripts/determinism_check.py`). The cause was not found: most likely an unrecorded package change on Day 1 between recording `requirements.txt` (commit `ff44102`) and running the benchmark (commit `07c603b`).
* **Lesson:** record `pip freeze` at the moment of every benchmark run, not only after installing tools. Also, the Day 1 `requirements.txt` was saved as UTF-16 (PowerShell `>`), which git treats as binary; `scripts/compare_requirements.py` reads both encodings.
